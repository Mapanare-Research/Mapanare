# Delta Review: v4.74.0 — `for await` Stream Async Iterator

> Two-reviewer delta review. New syntax: `for await x in stream { ... }`.

## Grammar diff

```lark
# New production:
for_await_stmt: KW_FOR KW_AWAIT NAME KW_IN expr block

# Added to stmt alternation:
| for_await_stmt
```

## AST + parser + semantic + lowering diff

- AST: `ForAwaitLoop` dataclass (var_name, iterable, body)
- Parser: `for_await_stmt` transformer
- Semantic: async context check, scope for loop variable
- Lower: desugars to for-loop pattern (__iter_has_next/__iter_next)

## Review questions

1. Does the desugar produce correct IR?
2. Does break exit cleanly without leaking the future?
3. Is the `for await` syntax defensible vs manual loop?

## Verdicts

### Rattler (primary) — PASS

Grammar matches DESIGN.md §3.6. The production is clean: `for await` is
two keywords, not a composite token. The desugaring to a for-loop with
iterator protocol is correct for the inline-resume model from v4.73.0.
Break exits the loop normally — no future to leak since the iteration is
synchronous (inline-resume).

### Coral (secondary) — PASS

The syntax is clean and matches the JavaScript/Python `async for` pattern
(prefix position). The `for await x in stream` reads naturally. The async
context check prevents accidental use in sync functions.

Note: the desugaring currently uses `__iter_has_next`/`__iter_next` which
is the same as a regular for loop. The async aspect comes from the
inline-resume model when the stream producer is an async fn. For true
async streams (I/O-backed), the desugaring would need `await stream.next()`
— that's a v5.x refinement.
